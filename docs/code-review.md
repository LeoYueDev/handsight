# Hindsight 代码评审与优化清单

> 评审日期：2026-11-17
> 评审范围：`src/` 全部 5 个模块 + `test/integration.ts`（只读代码，未运行）
> 总体评价：工程素养明显高于一般玩具项目，但有一个架构性短板和一个设计缺陷，"智能"部分很初级。约 7/10 的早期开源项目水平。

## 做得好的地方（保持，不要退化）

- **模块划分干净**：store / profiler / fileWatcher / index 职责单一，依赖只有 3 个，没有过度抽象
- **并发和持久化细节考虑周到**：
  - `store.ts:67` 数据目录独占锁 + 死进程 PID 回收（sql.js 整文件覆盖写，多实例互相覆盖）
  - `store.ts:210` Promise 链串行化写操作；500ms 防抖刷盘
  - `store.ts:162` memories 表 UNIQUE 约束迁移包在事务里，失败回滚
  - `profiler.ts` 增量游标持久化到 meta 表、画像刷新防抖 5s + 缓存 TTL 30s
- **SQL 全部参数化**，LIKE 通配符正确转义（`store.ts:376,722`），无注入风险
- **MCP 边界校验完整**：每个工具检查类型、范围、长度上限，批量上限 1000 条
- **fileWatcher 错误熔断**：连续失败 10 次暂停 60s；忽略列表覆盖常见构建目录和 `.env`
- **优雅退出**：SIGINT/SIGTERM → 取消定时器 → 停监控 → 刷盘 → 释放锁
- **集成测试走真实 MCP stdio 协议**，含负面用例

## 优化清单（按优先级排序）

### P1 — 会真实伤害用户的问题

- [x] **1. 持久化非原子写，崩溃即损坏数据库**（最小改动方案已完成；换驱动的彻底方案另行立项）
  - 位置：`store.ts:236` `flushSave()`
  - 问题：`db.export()` 整库导出后 `writeFileSync` 直接覆盖原文件，写到一半崩溃/断电 = 数据库损坏，全部记忆丢失。对"持久化记忆"服务是最不该有的风险。
  - 方案（最小改动）：写临时文件 + `fs.renameSync` 原子替换。
  - 方案（彻底）：换 `better-sqlite3` 或 Node 22 内置 `node:sqlite`，消除全内存 + 整库导出的架构短板（同步导出阻塞事件循环；上限 1 万条对话 × 64KB 理论最坏 640MB，撑不住）。README 说 sql.js 为免原生编译，属有意识取舍，但代价没兜住。
  - 验证：写入过程中模拟中断后 DB 仍可打开；现有集成测试全过。

- [x] **2. 项目级画像互相覆盖全局 AGENTS.md**（方案 A 已完成）
  - 位置：`profiler.ts:120` `updateAgentsMd()`
  - 问题：完全忽略 `project` 参数——刷新项目 A 的画像把 A 的偏好/决策写进全局 `~/.config/opencode/AGENTS.md`，刷新项目 B 又覆盖掉。"最后刷新的项目"的上下文泄漏到所有项目会话，与 README 宣称的"多项目隔离"矛盾。
  - 关联：`index.ts:804,837` 删除/更新记忆后 `scheduleRefresh()` 不带 project，刷的是全局画像而非记忆所属项目。
  - 方案：项目画像写入项目级配置（或按项目分标记区间），全局 AGENTS.md 只放全局画像。
  - 验证：刷新两个不同项目的画像后，各自内容互不覆盖；全局区只含全局数据。

### P2 — 数据安全与行为正确性

- [ ] **3. AGENTS.md 写入非原子 + 重排用户手写内容**
  - 位置：`profiler.ts:174,180`
  - 问题：对用户手写内容做 `.trim()` 重排；`writeFileSync` 直接覆盖，崩溃可能截断用户配置文件。自动修改用户配置文件应更克制。
  - 方案：临时文件 + rename；保留用户内容原样，只替换 HINDSIGHT 标记区间。

- [ ] **4. 对话原文明文存储，无脱敏**
  - 位置：`store.ts` conversations 表
  - 问题：对话可能含密钥、内部代码，明文存家目录。
  - 方案：至少提供开关/文档说明；可选做常见 secret 模式脱敏。

- [ ] **5. `ignoreInitial: false` 导致存量文件灌满事件表**
  - 位置：`fileWatcher.ts:54`
  - 问题：每次开始监控把整个目录树所有存量文件记成 "create"，瞬间灌满事件表、污染统计。
  - 方案：改为 `ignoreInitial: true`（或 ready 后再挂事件）。
  - 验证：监控已有文件的目录，事件表不出现存量文件的 create 记录。

- [ ] **6. 自动清理只在启动时跑一次**
  - 位置：`store.ts:159` `init()` → `cleanup()`
  - 问题：长期运行进程不会按 30 天滚动清理，与 README 描述不符。
  - 方案：定时器周期清理（如每小时），或每次写入路径低频触发。

### P3 — 一致性与健壮性细节

- [ ] **7. 排序/分页按 timestamp 而非 id，同毫秒顺序不稳定**
  - 位置：`store.ts` 各查询；`index.ts:582` 批量写入 `now + i` 毫秒 hack
  - 方案：排序统一用 `id`（单调），去掉 `now + i` hack。

- [ ] **8. 搜索相关度打分未做 LIKE 转义**
  - 位置：`store.ts:741` scoreExpr
  - 问题：term 没转义 `%`/`_`，与 WHERE 条件（已转义）行为不一致，含通配符的词计分错误。
  - 方案：scoreExpr 中的 term 同样转义并加 ESCAPE。

### P4 — 核心价值与可维护性（较大改动，需先讨论方案）

- [ ] **9. 记忆提取过于初级**
  - 位置：`profiler.ts:7-20,249-275`
  - 问题：中英文关键词子串匹配，命中后整条消息原样存为记忆；置信度 0.7/0.8/0.9 是魔法数；误报率高（"不需要"任何语境都算 dislike）；无去重归并、衰减、冲突消解。
  - 关联：`profiler.ts:216` `buildProfile` 按第一个 `:` 切 key/value，消息里随便一个冒号就能造出奇怪画像条目。
  - 方向：提取结构化 key/value 而非存整句；可选 LLM 辅助提取；置信度机制需要真实依据。

- [ ] **10. index.ts 1076 行，Schema 与校验双份手写**
  - 位置：`index.ts`
  - 问题：19 个工具的 JSON Schema 手写一遍、switch 里校验再手写一遍，人肉保持同步。
  - 方案：用 zod（MCP SDK 原生支持）统一 schema + 校验，可砍掉约一半代码。

- [ ] **11. 测试偏弱**
  - 位置：`test/integration.ts`
  - 问题：前 6 个用例只 `console.log` 无断言；文件监控靠固定 `sleep(1500)`，慢机器闪断；无单元测试——锁回收、迁移、防抖这些精细逻辑最需要单测。
  - 方案：补断言；轮询等待替代固定 sleep；为 store/profiler 关键路径补单测。
